# Current Product and Runtime Facts

This is the canonical current-behavior table for product, runtime, storage and delivery. Update the relevant row when behavior changes; other guides expand these facts rather than maintaining a second implementation tracker. This describes the working implementation, including audit fixes that have not yet been released. It does not claim that an installed or previously published version has these fixes.

`AGENTS.md` defines the product constraints. Source, tests and observed behavior establish what the implementation does; a conflict with a product constraint requires a decision or implementation correction, rather than automatically making the implementation authoritative.

| Area | Current fact | Implementation and detailed guide |
| --- | --- | --- |
| Product boundary | A lightweight GitHub-native development coordination tool for individuals and small teams using coding-agent CLIs. GitHub is the identity, permission and collaboration source. Local state is an execution projection, not a separate team account or authoritative issue/review database. | [Repository constraints](../AGENTS.md), [product](product.md) |
| Clients and owner | Electron and WebUI share one independent ordinary Node runtime per profile/config owner. Business state, PTYs and watchers belong to that runtime; Electron keeps native windows, menus and desktop capabilities. | [Architecture](architecture.md), `electron/runtime-client.ts`, `src/runtime/application-runtime.ts` |
| Startup | `sharkbay serve` starts the runtime in the foreground. `sharkbay service enable` registers a user service on macOS or Linux. A packaged Electron client connects to the running local service before loading the workspace. The development Electron launcher can start a source runtime. | `src/server/cli.ts`, `src/server/user-service.ts`, `electron/runtime-client.ts`, [release](release.md) |
| Shutdown | Closing or updating the desktop client disconnects it without stopping runtime terminals. Explicit runtime stop rejects new/queued work, cancels owned jobs and cleans up terminals and profile locks. An incompatible client does not silently replace a live runtime. | `src/server/main.ts`, `src/core/job-scheduler.ts`, [development](development.md) |
| Browser connection | By explicit product choice, loopback, RFC1918 and IPv4 link-local TCP peers can open the WebUI directly without a grant or cookie. Reachable devices on these networks can operate host projects and terminals. Other peers require a host-issued one-time grant exchanged for an HttpOnly SameSite=Strict session cookie. Host/Origin and command checks remain; forwarded headers do not grant access. Revoke invalidates explicit grants/sessions but does not revoke local/LAN network trust. No separate user accounts are introduced. | `src/server/session-auth.ts`, `src/server/http-server.ts`, `src/renderer/bridge/web-bridge.ts` |
| Network address | The npm CLI defaults to `127.0.0.1:17777` and enables IPv4 LAN binding with `--lan`. The legacy direct runtime entry point retains its IPv4 wildcard default. With LAN binding, reachable trusted-network devices can operate host projects and terminals. | `src/server/cli.ts`, `src/server/main.ts`, `src/server/http-server.ts` |
| Terminal control | A desktop/browser client controls each PTY while other attached clients observe; explicit takeover transfers control. Observers scroll and select text locally and can hide tabs until the client reloads. The controller determines the shared terminal size, receives application mouse input, and can close the session. Reconnection attaches the existing terminal instead of creating another Agent. The controlling renderer answers terminal queries; the host headless emulator replies only when no controller is attached, avoiding duplicate input to interactive CLIs. | `src/runtime/terminal-state.ts`, `src/renderer/terminal-observer.ts`, [architecture](architecture.md) |
| Codex prompt attachments | Desktop and WebUI support choosing or pasting files into client-local drafts scoped to the terminal. PNG and JPEG files are sent as visual inputs. Other files are stored temporarily on the host and referenced by path in the prompt. Each prompt accepts up to four files totaling 64 MiB, with a limit of 8 MiB per visual attachment. Files are removed when the runtime stops. | `src/renderer/App.tsx`, `src/server/http-server.ts`, `src/shared/application-api.ts` |
| Telegram | Pairing and bot settings are local integrations. One PTY belongs to at most one Telegram user at a time; a new Telegram user taking over detaches the old mapping. This defines Telegram ownership and does not replace desktop/browser control rules. Approval callbacks are bound to user, chat, message, PTY and turn. | `src/main/telegram/service.ts`, `src/runtime/telegram-runtime.ts` |
| Projects and execution | Projects are explicitly configured local directories. Desktop and WebUI can add an existing host folder or clone a repository into a chosen host parent folder. Desktop uses native folder dialogs; WebUI browses host directories or opens an absolute host path. Both register projects through the same runtime commands. The registered execution provider is LocalProvider. Container/WSL type scaffolding and historical SSH plans are not available execution providers. Removing a project removes its workspace entry, not its source repository. | `src/runtime/host-directories.ts`, `src/renderer/host-folder-picker.tsx`, `src/core/core-runtime.ts`, `src/providers/local/local-provider.ts`, `src/main/config.ts` |
| Git worktree sidebar | Desktop and WebUI share the sidebar that groups registered Git worktree roots under their repository. The active project shows Git worktrees and other local and `origin` branches, excluding `sharkbay-team-context` from the branch list. Refresh Git fetches branch updates from `origin`. Opening an origin-only branch creates a local tracking branch and worktree. Worktree and local branch deletion use Git's non-force operations. | `src/renderer/project-worktrees.tsx`, `src/main/worktree.ts`, `electron/preload.mts` |
| GitHub and local protocol | GitHub issue/PR information and repository permissions come through gh/Git. Optional repo-local Task Protocol supplies execution context and managed helpers. It does not replace GitHub Issues, PRs or reviews. Existing implementation details do not override that product boundary. | `src/main/github.ts`, `src/runtime/task-runtime.ts`, [Task Protocol](tasks.md) |
| File editing | Files are lazily listed. Supported text files can be opened, edited and saved in the built-in CodeMirror editor. Runtime path, size and content checks apply; external terminal editor/diff actions may coexist. | `src/renderer/code-editor.tsx`, `src/main/file-content.ts`, [product](product.md) |
| CodeGraph | Opening projects and observing file changes do not create/sync indexes. Build index / Sync index is a manual action. Cancellation and removal are coordinated by the runtime manager. A plugin being enabled is not proof that every project has an initialized index. | `src/core/codegraph-manager.ts`, `src/renderer/App.tsx` |
| Plugins and profiles | Eight bundled plugin definitions register in code through PluginHost. Machine profiles support tool installation preconditions; Agent listing has its own enabled-detector shortcut. Project-profile implementation exists without an application/UI consumer. Filesystem installed-plugin discovery, arbitrary third-party plugin execution and marketplace installation are not shipped capabilities. | `src/plugins/bundled-plugins.ts`, `src/plugins/plugin-host.ts`, `src/profiles/profile-orchestrator.ts` |
| Shared local storage | Default runtime profile is `~/.sharkbay/runtime/`; explicit data-dir and config overrides are supported. JSON config, token-usage SQLite, caches and local control endpoints remain on the host. Renderer layout and browser storage have their own client locations. | [Architecture storage map](architecture.md#runtime-data), `src/runtime/profile-lock.ts`, `src/runtime/control-client.ts` |
| Repository storage | Optional managed files live under `.sharkbay/`; task context can sync through the repository's `sharkbay-team-context` branch when configured and permitted. Git metadata paths are obtained from Git so linked worktrees use the correct shared directory. No proprietary cloud database is introduced. | `src/main/harness.ts`, `src/main/teamwork-sync.ts`, [Task Protocol](tasks.md) |
| Usage costs | Usage reports use provider events/credits where supplied and otherwise preserve unknown cost. There is no built-in model-price catalogue or automatic synthetic USD estimate. | `src/main/token-usage-collector.ts`, `src/main/token-usage-db.ts` |
| Build and bundle | `npm run pack:runtime` builds the independent Runtime and WebUI npm tarball. Its SQLite and PTY dependencies use the host Node ABI. The macOS desktop package contains the client and connects through the same-user control endpoint. | `package.json`, `scripts/pack-runtime-npm.mjs`, [release](release.md) |
| Updates and release | The updater uses the configured public SharkUI/SharkBay GitHub Releases feed. Local pack and formal distributable signing are different workflows. Formal distribution requires Developer ID signing, notarization and artifact verification. A source commit does not update an installed app or host 103. | [Release guide](release.md), `src/main/app-updates.ts` |
| Verification status | Module tests and static checks do not establish desktop, complete runtime, update-installation or target-host acceptance. Commands that start those surfaces require the relevant authorized environment. Historical audit findings describe their fixed target commit, not the current remediation state. | [Testing](testing.md), [audit report](audit/2026-11-17/report.md), [fix reports](audit/2026-11-17/fixes/) |

Historical designs such as [execution target profiles](execution-target-profiles.md), [workspace model](workspace-model.md) and [workspace agent platform](workspace-agent-platform.md) contain proposals and earlier assumptions. They do not establish current features or authorization to implement them. Resolve design decisions against the repository constraints and this table before making changes.
