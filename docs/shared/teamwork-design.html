SharkBay Teamwork Feature Design

SharkBay 的 Teamwork 功能目标是让小团队成员各自电脑上的 agent 共享项目上下文、工作记录和交接信息，同时保持 local-first，不引入 SharkBay 自己的账号系统。

Status: proposal Branch: teamwork Date: 2026-05-11 Storage: GitHub repo context branch
Core Decision

Teamwork mode 使用 gh 作为 GitHub 身份和权限入口，使用 worktree-local .sharkbay/ 保存 active tasks、file claims 和 harness 状态； 任务结束后再把 compact task record 导出到 GitHub repo 的专用 context 分支。Harness 不是启动 agent 的 wrapper，而是为 agent 提供可读、可执行、 可验证、可反馈的项目工作环境。长期产品和开发决策进入 docs/， human-readable help site 由 SharkBay 本地生成。 

Local SharkBay app:
- no SharkBay login
- requires gh auth for Teamwork
- stores active task states and file claims in .sharkbay/
- syncs completed task records to the context branch
- reads source docs from the normal code branch
- generates local help site outside the repo
- exposes team context through MCP

Management Model

团队工作中的 agent 调用记录属于工作职责的一部分，默认可以在团队内透明。 Teamwork 的主要边界不是个人隐私，而是 secrets、客户数据、production credentials 和本地 token。

  • 团队成员可以看到 completed tasks、final summaries、agent run summaries 和 commit evidence。
  • GitHub Issues 是 task 的可选来源，不是唯一任务系统。
  • 重要产品和开发决策走 docs/。
  • 高风险内容需要 redaction 规则，避免把 secret 写入共享 context。
  • 审计记录应该标明 GitHub actor、agent、branch、commit 和时间。

Identity Model

SharkBay 不做成员注册。Teamwork 功能要求本机安装并登录 gh，成员身份和 repo 权限完全复用 GitHub。

  • gh api user 提供 verified GitHub login 和 user id。
  • gh api repos/OWNER/REPO/collaborators/LOGIN/permission 提供 permission 和 role_name。
  • 本地 git config user.name 和 user.email 只作为辅助信息。

Architecture

1. Detect 解析 local repo 的 origin，识别 owner/repo、 branch、commit 和 dirty state。
2. Verify 使用 gh 验证 GitHub actor 和 repo permission。Teamwork 写入要求 permission 至少是 write。
3. Fetch 拉取共享 context 分支 sharkbay-team-context，读取 已完成 task 的摘要和历史 run summaries。
4. Context 从 .sharkbay/task/active-tasks.json、file-claims.json、repo docs、GitHub Issues、 commits 和历史 summaries 生成 agent 可用的 context pack。
5. Record task 进行中只更新本地 .sharkbay/。task 结束并 commit 后， 导出 compact record 到 context branch。
Harness Reframe

根据 OpenAI harness engineering 的思路，SharkBay harness 应被理解为 project-local agent operating environment，而不是简单的 agent launcher、task runner 或 dirty-file guard。它的职责是提升 agent 的杠杆： 帮 agent 找到上下文、使用工具、运行验证、读取反馈，并把有价值的结果沉淀回项目。 参考：OpenAI Harness Engineering。 

Harness surfaces:
- Context map: docs, AGENTS guide, active tasks, file claims, prior task summaries
- Tool surface: git, gh, npm scripts, dev services, browser automation, logs
- Verification surface: tests, builds, screenshots, console errors, app health
- Feedback loop: task -> changes -> verification -> commit -> synced context
- Maintenance loop: stale docs, abandoned .sharkbay state, failed context syncs, context hygiene

.sharkbay/ task files 和 sharkbay-team-context 只是这个 harness 的 task context protocol。它们不等于 harness 本身。

Task Model

Task 是可审计的工作单元，Run 是 task 期间某个 agent 做过的一段工作证据流水。用户接受的是 issue 或提出的是需求； task 一定由某个用户在自己的 SharkBay 里创建。

  • Task 来源可以是用户自然需求、GitHub Issue、agent 建议或 repo owner 分配。
  • 默认 task 只有 brief、acceptance、runs、verification、final summary 和 commit。
  • Task 类型只有两种：quick task 和 task。
  • quick task 不走重流程，但仍必须导出到 shared context，并标记 mode: quick。
  • 同一 worktree 可以有多个 active editing tasks；隔离边界是文件级 ownership，而不是整个 worktree。
  • Task 只能以 committed+synced、blocked 或 abandoned 结束；file claims 按结束状态释放或保留。

MCP Role

MCP 是 agent 访问 team context 的接口，不是 storage 本身。Storage 是 repo 文件，MCP 工具负责把文件整理成 agent 可用的上下文。

  • get_project_context
  • search_team_context
  • get_current_task
  • update_current_task
  • read_related_runs
  • record_run_event
  • prepare_task_export

MCP Scope

MVP 必须包含 agent 获取跨成员上下文的入口，否则 Teamwork 只剩本地 task 文件协议。 因此 get_project_context 和 search_team_context 属于 MVP。

Tool Scope Purpose
get_project_context MVP 返回 compact project context：active tasks、file claims、repo docs index、recent completed tasks、recent run summaries、GitHub issue/PR hints。
search_team_context MVP 对 docs/、context branch records 和 local task summaries 做关键词搜索，返回短摘要和文件引用。
get_current_task MVP 读取当前 selected task 的 compact task state；多 active task 时由 SharkBay 传入 task id。
update_current_task MVP 更新指定 active task 的 brief、acceptance、summary、status 或 verification notes。
record_run_event MVP 追加本地 run event 到 .sharkbay/task/runs/。
prepare_task_export MVP 生成待用户确认的 compact export preview。
read_related_runs Post-MVP 按 task、issue、file、agent 或 commit 聚合历史 runs；MVP 先由 get_project_context 和 search 覆盖。
Review Of Previous Design

前一版设计把 harness 写得过窄，主要像 task wrapper、agent launcher 和 worktree guard。这会把注意力放在“怎么启动 agent”和“怎么定义 run 边界”上， 而不是放在 agent 需要什么工作环境才能更可靠。

  • 保留：.sharkbay/ 作为 worktree-local active tasks 和 file claim protocol。
  • 保留：completed task 导出到 sharkbay-team-context。
  • 保留：gh 作为 Teamwork 身份和权限来源。
  • 修正：harness 不是 agent 启动器，启动 agent 只是 harness 可选能力之一。
  • 修正：不再设计 formal task；只有 quick task 和 task。
  • 修正：review/spec/design 不作为默认强制状态机，只作为普通 task brief/acceptance 的可选内容。
  • 修正：共享 context 不应记录冗长过程，只导出 compact outcome 和关键 evidence。
Why This Helps Team Agents

最初目标是让不同成员本机上的不同厂商 agent 共享工作上下文。当前设计共享的是 source docs、tasks、runs、commits、GitHub Issues/PRs 和本地生成的 help site， 而不是同步各家 agent 的私有聊天意识。 

Shared across team agents:
- docs/: durable product and engineering decisions
- completed tasks: compact task outcomes and commit links
- run summaries: task-scoped agent evidence
- GitHub Issues/PRs: external collaboration facts
- commits: final code change facts
- local help site: human-readable synthesis

这能减少重复解释上下文、避免不同 agent 重复踩坑，并把每个变更都绑定到 task、run、verification 和 commit。可靠性来自 file claim guard、 commit boundary、GitHub identity 和 cross-agent evidence。

Local Worktree State

不需要 SQLite。每个 worktree 使用本地 ignored .sharkbay/ 目录保存 active tasks、file claims、harness events 和 context pack。 这个目录不进 repo，只服务当前 worktree。一个 worktree 可以同时有多个 active editing tasks，只要它们不 claim 同一个文件。 

.sharkbay/
  task/
    active-tasks.json
    file-claims.json
    runs/
      r01HY.jsonl
  context/
    context-pack.md
  harness/
    session.json
    events.jsonl

Repo 的 .gitignore 应包含 .sharkbay/。这样 agent、 harness 和用户都能直接看到协议文件，多 worktree 也天然隔离。

File Claim Guard

并行 task 的冲突边界是文件。agent 准备修改文件前，必须先通过 harness claim 文件；harness 检查 Git dirty state 和 file-claims.json 后决定是否允许。 这个规则必须在工具层执行，不能只靠 prompt 约束 agent。 

Claim rules:
- clean + unclaimed file: allow, then add to current task ownedFiles
- already claimed by current task: allow
- claimed by another active task: pause current task as waiting_for_file
- dirty + no known owner: pause current task as dirty_unowned_file
- deleted/renamed file: require explicit claim for old path and new path
- generated files: claim only if they will be committed with this task

Task commit 时只 stage 自己的 ownedFiles。如果 verification 在同一个 worktree 中运行，结果必须标记为 combined worktree；需要更强保证时， SharkBay 应提示用户在 clean temporary worktree 或独立 worktree 中做 isolated verification。

Task Conflict Flow

当 task 要修改被其他 task claim 的文件时，暂停的是当前 task，不是整个 worktree。用户可以继续推进其它不相关 task；等占用文件的 task commit/sync 或释放 claim 后，再回到暂停 task 点击 continue。 

Task B wants src/browser/fullscreen.ts
-> file claimed by Task A
-> Task B status: waiting_for_file
-> user finishes Task A and commits ownedFiles
-> SharkBay sees file clean/unclaimed
-> user continues Task B
-> harness rebuilds context pack and resumes agent

File Claim State

file-claims.json 是 worktree-local 的轻量 lock table，不是团队级锁。 它只用于防止同一个 worktree 内多个本地 agent 互相覆盖 dirty files。 

{
  "claims": {
    "docs/shared/teamwork-design.html": {
      "taskId": "t01HX",
      "status": "dirty",
      "claimedAt": "2026-05-15T10:12:00Z"
    },
    "src/renderer/browser.ts": {
      "taskId": "t01JQ",
      "status": "clean",
      "claimedAt": "2026-05-15T10:18:00Z"
    }
  }
}

Active Task Recovery

SharkBay 启动或进入项目时必须检查 .sharkbay/task/active-tasks.json、 .sharkbay/task/file-claims.json 和 .sharkbay/harness/events.jsonl。 如果某个 active task 超过默认 24 小时没有 event 更新，或上次 session 没有正常关闭， 就标记为 stale。

术语边界：export 是生成 compact task package；sync 是把 package 写入并推送到 sharkbay-team-context。UI 只向用户暴露 sync 状态，例如 pending sync 或 sync failed。

  • resume: 继续指定 task，保留它的 owned files 和 run logs。
  • finish/sync: 用户确认 summary、verification 和 commit 后生成 package 并同步到 context branch。
  • mark blocked: 导出 blocked summary，释放或保留 file claims 由用户决定。
  • abandon: 只有该 task 的 owned files clean，或用户明确 stash/clean 后才允许。

Sync 或 abandon 失败必须保持 active task 文件不删除，UI 显示明确的 pending/recovery 状态。 不允许静默丢弃 .sharkbay/ 状态。

Shared Storage

共享 context 使用普通文件保存，放在独立分支 sharkbay-team-context。它只接收完成后的 compact task package， 不保存 active tasks 的频繁过程更新。不使用 SharkBay backend；搜索直接依赖 rg、jq 和文件读取。 

.sharkbay-team-context/
  project.md
  tasks/
    2026/
      05/
        20260511T220000Z-t01HX-browser-fullscreen.md
  runs/
    2026/
      05/
        11/
          20260511T220000Z-r01HY-task-t01HX.jsonl

文件名规则： <UTC timestamp>-<taskId or runId>-<slug>.<ext>。 GitHub user id、machine id、permission、branch 和 commit 放进 frontmatter 或 JSONL metadata，不放进文件名。这样保留排序和唯一性，同时降低 terminal 阅读和 tab-complete 成本。

Task Records

Task 可以来自用户直接提出的需求，也可以来自 GitHub Issue。Issue 是团队级请求； task 是某个用户在某台机器上执行这个请求时创建的可审计工作单元。 进行中状态保存在 .sharkbay/task/active-tasks.json， 文件 ownership 保存在 .sharkbay/task/file-claims.json； 完成后导出到 context branch。

Task Modes

Harness 应该按改动规模降级，但所有修改都应该留下 shared context。 quick task 是快速修改，task 是普通工作。 

Quick task:
- mode: quick
- direct edit, test, commit
- commit message carries the explanation
- synced to shared context with compact summary

Task:
- mode: task
- brief
- acceptance
- run summaries
- verification
- final summary
- commit

Run Records

Agent run 使用 append-only JSONL，先写入 .sharkbay/task/runs/。 Task 完成时只导出摘要和关键证据到 context branch，避免共享上下文被过程噪音污染。 

{"kind":"run_started","taskId":"t01HX","runId":"r01HY","project":"SharkUI/SharkBay","branch":"browser-fullscreen-shortcut","commit":"451cf567","author":{"githubLogin":"SharkUI","githubUserId":3960864},"machine":{"shortId":"m7f3a6"},"agent":{"id":"codex"},"createdAt":"2026-05-11T20:40:00Z"}
{"kind":"shell_command","taskId":"t01HX","runId":"r01HY","cmd":"npm test","exitCode":0,"createdAt":"2026-05-11T21:10:00Z"}
{"kind":"files_touched","taskId":"t01HX","runId":"r01HY","files":["src/main/browser-tabs.ts","tests/browser-tabs.test.ts"],"createdAt":"2026-05-11T21:12:00Z"}
{"kind":"run_summary","taskId":"t01HX","runId":"r01HY","body":"Implemented fullscreen shortcut handling for SharkBay browser and verified browser-tabs tests.","createdAt":"2026-05-11T21:20:00Z"}

Help Site

Help site 是 post-MVP 的本地生成物，不进 repo。MVP 可以先在 Tasks tab 直接展示 active tasks、file claims、completed task summaries 和 search results。

  • 触发：MVP 后先支持用户手动生成；后续可在 fetch context branch、完成 sync、或打开 Tasks tab 时增量刷新。
  • 内容：默认包含 active tasks、file claim 状态、最近 50 个 completed tasks、最近 90 天 run summaries、相关 docs index、open GitHub issues/PRs 摘要。
  • 范围：完整历史不默认渲染，可通过 search 或 archive page 按需展开。
  • 位置：~/Library/Application Support/SharkBay/help-sites/<project-id>/。

Member Information

不按成员建目录。成员身份放在每条 context record 的 metadata 中，而不是塞进长文件名。 这样文件仍然按类型和时间聚合，同时 UI 可以按成员、机器、agent、branch、时间和状态过滤。

Field Purpose Source
githubLogin, githubUserId 团队视角下的可信 actor identity。 gh api user
permission, roleName 记录写入时该成员对 repo 的权限。 GitHub collaborators permission API
gitName, gitEmail 辅助对照 commit author。 git config
hostname, machineId 标明哪台开发机启动了 agent。同一 GitHub 用户多台电脑时用于区分写入来源。 local machine

machineId 由 SharkBay 在每台机器首次启用 Teamwork 时生成 UUID， 保存在本机 app config 中。短码例如 m7f3a6 只用于 UI 展示； 完整 UUID 或稳定 short id 写入 metadata，避免 hostname 变更或重复导致身份不稳。

Conflict Policy

Teamwork context 的冲突策略是 append-only、unique file 和 duplicate-on-conflict。 SharkBay 不做 destructive merge，不覆盖其他成员写入，也不把 Git conflict 暴露给用户。

  1. 写入前 fetch 最新 sharkbay-team-context。
  2. 在临时 worktree 中新增唯一文件并 commit。
  3. push 成功则完成。
  4. 如果 push rejected，fetch 最新后 rebase 并重试。
  5. 如果 rebase 真的发生文件冲突，abort rebase，基于最新远程重新生成唯一文件名，再 commit + push。
  6. 如果仍失败，将待同步文件保存到本机 pending queue，UI 显示 Team context pending sync。

语义冲突不在 Git 层解决。例如两个 agent runs 对同一个 issue 给出互相矛盾的建议， SharkBay 保留两条记录。真正的产品或架构结论应该通过 GitHub Issue/PR 讨论后进入 docs/，而不是在 runtime context 分支里合并成 decision。

Search

团队小的时候不需要数据库索引服务。SharkBay 可以直接用 rg 搜索文件，再按 frontmatter 或 JSONL 字段解析结果。

rg '"kind":"run_summary"' .sharkbay-team-context/runs
rg "taskId: t01HX" .sharkbay-team-context/tasks
rg '"taskId":"t01HX"' .sharkbay-team-context/runs
rg "githubUserId: 3960864" .sharkbay-team-context
rg "shortId: m7f3a6" .sharkbay-team-context

Tasks UI

现有 SharkBay 是三栏工作台：左侧项目列表、中间 terminal/browser、右侧 detail panel。 Tasks 应作为 Project detail 的第一个 tab，放在 Git 左边，不新增独立 dashboard。

  • Status subpanel: 一行 facts，显示 repo、branch、worktree、gh actor、repo permission、context sync、active task count、claimed files count。
  • Task list: Tasks 是一个一体化列表，不按 active/completed 拆 panel，也不再套一个写着 Tasks / All 的 subpanel 标题框。列表直接出现在 Teamwork status 下方。
  • Task numbering: 显示编号使用全项目递增序号，前缀表示类型：T1、T2、Q3、T4、Q5。T 是 task，Q 是 quick task；数字不按类型分别计数。
  • Task order: task 按创建时间倒序显示，最新的在最上面；编号仍然保持创建时分配的全局序号。
  • Task row: 编号和 title 必须在同一行作为主视觉，title 不应被弱化成小字。第二行才显示状态、owner/agent、claimed files count 和 verification scope。sync failed、waiting_for_file、dirty_unowned_file 都是 task row 状态；waiting 使用黄色 warning 状态。
  • Task detail: 点击 task 后列表消失，右侧 panel 进入 task detail drilldown。Detail 顶部有 back button 返回 task list；标题下不重复 project/type/status。详情只展示任务事实，例如 status、branch/base、verification、sync result、blocked-by 文件和 related runs。正常 claimed files 默认不展示，只有 claim 冲突、dirty unowned 或阻塞其它 task 时才露出。
  • Task creation: MVP mockup 不放 Quick task、Task、Create from issue 三个并列表意不明的按钮；创建入口后续需要重新设计。
  • Attention rows: 只显示非 task 归属的风险，例如 context branch risk、gh readiness 问题；task 自身问题留在对应 task row 和 task detail。

Issues 和 Help site 不进入 MVP 首屏：Issues 只作为 Create from issue 的选择器； Help site 是 post-MVP 本地生成物。

Boundaries
  • 基础 SharkBay 不要求 gh，扫描项目、开终端、本地 agent run 仍可用。
  • Teamwork 功能要求 gh authenticated。
  • 写入共享 context 要求 GitHub repo permission 至少是 write。
  • Policy 配置建议要求 maintain 或 admin。
  • .sharkbay/ 保存本地 active tasks、file claims 和 harness state，必须加入 .gitignore。
  • 同一 worktree 可以有多个 active editing tasks；并发边界是文件 claim，不是 worktree clean。
  • agent 修改文件前必须 claim file；遇到被其他 task claim 或 dirty 但无 owner 的文件时，当前 task 暂停。
  • 同一用户可以在多个 worktree 有多个 active tasks，但 UI 必须显式展示 repo、branch、worktree 和 claimed files。
  • Runtime context 分支只保存完成后的 tasks/ 和关键 runs/ 摘要。
  • GitHub Issues 是 task 的可选来源；重要决策使用 docs/。
  • Raw transcript 可以后续再做，MVP 先记录可审计摘要和关键 events。
  • 严肃审计如果未来变强，再引入 SharkBay backend 或 GitHub App。

Architecture Risks

Risk Impact Mitigation
Context branch 被 force-push 或删除 团队历史丢失或不可追溯 创建 sharkbay-team-context 时提示配置 branch protection；SharkBay 检测 protected 状态并在未保护时显示风险。
gh token 过期或权限变化 用户以为 context 已同步，但实际失败 每次 sync 前运行 readiness check；失败时保留 pending sync，UI 明确显示未同步，不删除 active task。
同一 worktree 多个 active tasks 的验证被污染 Task A 的测试可能在 Task A + Task B 的组合状态下通过，不能证明单独提交 A 后通过 verification 记录必须标注 combined worktree 或 isolated clean state；高风险 task 提示使用独立 worktree 验证。
File claim stale 或 SharkBay 崩溃 文件被旧 task claim，导致新 task 无法继续 启动时检测 stale active tasks 和 file claims，提供 resume、release claim、finish/sync、mark blocked、abandon recovery options。

  2. 把 .sharkbay/ 加入 .gitignore，并定义 .sharkbay/task/active-tasks.json 和 .sharkbay/task/file-claims.json。
