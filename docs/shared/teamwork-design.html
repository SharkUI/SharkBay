SharkBay Teamwork Feature Design

SharkBay 的 Teamwork 功能目标是让小团队成员各自电脑上的 agent 共享项目上下文、工作记录和交接信息，同时保持 local-first，不引入 SharkBay 自己的账号系统。

Status: proposal Branch: teamwork Date: 2026-05-11 Storage: GitHub repo context branch
Core Decision

Teamwork mode 使用 gh 作为 GitHub 身份和权限入口，使用 worktree-local .sharkbay/ 保存 active tasks、file claims 和 harness 状态； 任务结束后再把 compact task record 导出到 GitHub repo 的专用 context 分支。Harness 不是启动 agent 的 wrapper，而是为 agent 提供可读、可执行、 可验证、可反馈的项目工作环境。长期产品和开发决策进入 docs/， human-readable help site 由 SharkBay 本地生成。 

Local SharkBay app:
- no SharkBay login
- requires gh auth for Teamwork
- stores active task states and file claims in .sharkbay/
- syncs completed task records to the context branch
- reads source docs from the normal code branch
- generates local help site outside the repo
- exposes team context through MCP

Management Model

团队工作中的 agent 调用记录属于工作职责的一部分，默认可以在团队内透明。 Teamwork 的主要边界不是个人隐私，而是 secrets、客户数据、production credentials 和本地 token。

  • 团队成员可以看到 completed tasks、final summaries、agent run summaries 和 commit evidence。
  • GitHub Issues 是 task 的可选来源，不是唯一任务系统。
  • 重要产品和开发决策走 docs/。
  • 高风险内容需要 redaction 规则，避免把 secret 写入共享 context。
  • 审计记录应该标明 GitHub actor、agent、branch、commit 和时间。

Identity Model

SharkBay 不做成员注册。Teamwork 功能要求本机安装并登录 gh，成员身份和 repo 权限完全复用 GitHub。

  • gh api user 提供 verified GitHub login 和 user id。
  • gh api repos/OWNER/REPO/collaborators/LOGIN/permission 提供 permission 和 role_name。
  • 本地 git config user.name 和 user.email 只作为辅助信息。

Architecture

1. Detect 解析 local repo 的 origin，识别 owner/repo、 branch、commit 和 dirty state。
2. Verify 使用 gh 验证 GitHub actor 和 repo permission。Teamwork 写入要求 permission 至少是 write。
3. Fetch 拉取共享 context 分支 sharkbay-team-context，读取 已完成 task 的摘要和历史 run summaries。
4. Surface 把 .sharkbay/tasks/*.json、.sharkbay/claims/file-claims.json、 repo docs、GitHub Issues、commits 和历史 summaries 暴露为 MCP tools 和可搜索文件。 SharkBay 不替 agent 做语义裁剪。
5. Record task 进行中只更新本地 .sharkbay/。task 结束并 commit 后， 导出 compact record 到 context branch。
Harness Reframe

根据 OpenAI harness engineering 的思路，SharkBay harness 应被理解为 project-local agent operating environment，而不是简单的 agent launcher、task runner 或 dirty-file guard。它的职责是提升 agent 的杠杆： 帮 agent 找到上下文、使用工具、运行验证、读取反馈，并把有价值的结果沉淀回项目。 参考：OpenAI Harness Engineering。 

Harness surfaces:
- Context map: docs, AGENTS guide, active tasks, file claims, prior task summaries
- Tool surface: git, gh, npm scripts, dev services, browser automation, logs
- Verification surface: tests, builds, screenshots, console errors, app health
- Feedback loop: task -> changes -> verification -> commit -> synced context
- Maintenance loop: stale docs, abandoned .sharkbay state, failed context syncs, context hygiene

.sharkbay/ task files 和 sharkbay-team-context 只是这个 harness 的 task context protocol。它们不等于 harness 本身。

Task Model

Task 是可审计的工作单元，Run 是 task 期间某个 agent 做过的一段工作证据流水。用户接受的是 issue 或提出的是需求； task 一定从用户和 agent client 的互动中产生，由所选 agent 按 SharkBay protocol 调用 MCP tools 创建或继续。

  • Task 来源可以是用户自然需求、GitHub Issue、agent 建议或 repo owner 分配，但创建动作由 agent client 通过 harness MCP tools 完成。
  • 默认 task 只有 brief、acceptance、runs、verification、final summary 和 commit。
  • Task 类型只有两种：quick task 和 task。
  • quick task 不走重流程，但仍必须导出到 shared context，并标记 mode: quick。
  • 同一 worktree 可以有多个 active editing tasks；隔离边界是文件级 ownership，而不是整个 worktree。
  • Task 只能以 committed+synced、blocked 或 abandoned 结束；file claims 按结束状态释放或保留。

Task identity 使用随机或 hash-derived 的 6 位短 tag，例如 A7K3P9。 taskTag 是 UI 和团队讨论里的短引用；完整 taskId 使用 <taskTag>-u<githubUserId>-m<machineId>， 例如 A7K3P9-u3960864-m7f3a6。不再使用顺序编号，因为 Teamwork 启用后 task list 会展示所有成员的 tasks，顺序编号没有团队语义。

MCP Role

MCP 是 agent 访问 team context 和 task lifecycle 的接口，不是 storage 本身。 Storage 是本地 .sharkbay/ 文件、正常 repo docs 和 context branch records 的组合；MCP 工具负责把这些文件整理成 agent 可用的上下文，并执行受控写入。

  • get_project_context - MVP
  • search_team_context - MVP
  • create_or_continue_task - MVP
  • get_task - MVP
  • update_task - MVP
  • claim_files - MVP
  • release_file_claims - MVP
  • record_run_event - MVP
  • prepare_task_export - MVP
  • read_related_runs - Post-MVP

MCP Scope

MVP 必须包含 agent 获取跨成员上下文的入口，否则 Teamwork 只剩本地 task 文件协议。 因此 get_project_context 和 search_team_context 属于 MVP。

Tool Scope Purpose
get_project_context MVP 返回 compact project context：active tasks、file claims、repo docs index、recent completed tasks、recent run summaries、GitHub issue/PR hints。
search_team_context MVP 对 docs/、context branch records 和 local task summaries 做关键词搜索，返回短摘要和文件引用。
create_or_continue_task MVP 由 agent 在理解用户意图后调用；根据 title/source/mode 创建 task，或根据 taskId/related issue/当前对话继续已有 task。
get_task MVP 读取指定 taskId 的 compact task state。必须显式传入 taskId，不从 UI selection、terminal session 或 recent history 推断。
update_task MVP 更新指定 taskId 的 brief、acceptance、summary、status 或 verification notes。
record_run_event MVP 追加本地 run event 到 .sharkbay/task-runs/。
claim_files MVP 原子 claim 一个或多个文件；成功后写入 file-claims.json，失败时返回 waiting_for_file 或 dirty_unowned_file。
release_file_claims MVP 在 task commit/sync、blocked、abandon 或 recovery 时释放指定 task 的 file claims。
prepare_task_export MVP 生成待用户确认的 compact export preview。
read_related_runs Post-MVP 按 task、issue、file、agent 或 commit 聚合历史 runs；MVP 先由 get_project_context 和 search 覆盖。
Review Of Previous Design

前一版设计把 harness 写得过窄，主要像 task wrapper、agent launcher 和 worktree guard。这会把注意力放在“怎么启动 agent”和“怎么定义 run 边界”上， 而不是放在 agent 需要什么工作环境才能更可靠。

  • 保留：.sharkbay/ 作为 worktree-local active tasks 和 file claim protocol。
  • 保留：completed task 导出到 sharkbay-team-context。
  • 保留：gh 作为 Teamwork 身份和权限来源。
  • 修正：harness 不是 agent 启动器，启动 agent 只是 harness 可选能力之一。
  • 修正：不再设计 formal task；只有 quick task 和 task。
  • 修正：review/spec/design 不作为默认强制状态机，只作为普通 task brief/acceptance 的可选内容。
  • 修正：共享 context 不应记录冗长过程，只导出 compact outcome 和关键 evidence。
Why This Helps Team Agents

最初目标是让不同成员本机上的不同厂商 agent 共享工作上下文。当前设计共享的是 source docs、tasks、runs、commits、GitHub Issues/PRs 和本地生成的 help site， 而不是同步各家 agent 的私有聊天意识。 

Shared across team agents:
- docs/: durable product and engineering decisions
- completed tasks: compact task outcomes and commit links
- run summaries: task-scoped agent evidence
- GitHub Issues/PRs: external collaboration facts
- commits: final code change facts
- local help site: human-readable synthesis

这能减少重复解释上下文、避免不同 agent 重复踩坑，并把每个变更都绑定到 task、run、verification 和 commit。可靠性来自 file claim guard、 commit boundary、GitHub identity 和 cross-agent evidence。

Local Worktree State

不需要 SQLite。每个 worktree 使用本地 ignored .sharkbay/ 目录保存 active tasks、file claims、harness events、tool manifest 和 protocol。 这个目录不进 repo，只服务当前 worktree。一个 worktree 可以同时有多个 active editing tasks，只要它们不 claim 同一个文件。 

.sharkbay/

    A7K3P9-u3960864-m7f3a6.json
    B4N8Q2-u3960864-m7f3a6.json
  task-runs/
    A7K3P9-u3960864-m7f3a6-r01HY.jsonl
  task-packages/
    A7K3P9-u3960864-m7f3a6-task-package.md
  claims/
    file-claims.json
  cache/
    github-users.json
  harness/
    protocol.md
    tools.json
    session.json
    events.jsonl

Harness install 不修改 repo 文件，包括 .gitignore。SharkBay 应把 .sharkbay/ 写入本地 .git/info/exclude，并在 stage/commit 前主动阻止 harness runtime files 进入 repo。这样每个项目成员可以有自己的 client、MCP 和 harness 配置。

这里的 repo 边界指正常代码分支和开发 worktree。团队共享记录仍写入专用 sharkbay-team-context 分支；它只保存 completed task packages， 不保存任何成员本机的 harness install/config/runtime files。

Local Harness Entry Files

SharkBay 不能假设所有 agent client 都读同一个入口文件，也不能把 harness instruction files 写进 repo。安装 harness 时，只在本地 .sharkbay/ 里生成 client-specific entry files。它们不保存当前 task 状态，只负责把 agent 引导到同一个本地 runtime protocol。

Installation Flow

Harness 安装只影响当前成员的本机项目配置，不产生需要 commit 的 repo 变更。 安装分三层：worktree-level runtime state、client-level project adapter、 run-level generated files。

  1. Open project: SharkBay 检测 repo root、Git remote、当前 branch、worktree path 和本机已安装的 agent clients。
  2. Protect repo: SharkBay 不修改 .gitignore，只把 .sharkbay/ 写入本地 .git/info/exclude，并在 stage/commit guard 中阻止 harness files 进入 repo。
  3. Initialize local state: SharkBay 在当前 worktree 创建 ignored 的 .sharkbay/ 目录、machine id、空的 tasks/、claims/file-claims.json 和 harness/。
  4. Prepare runtime protocol: SharkBay 生成或更新 .sharkbay/harness/protocol.md、tools.json 和 instructions/*.md。
  5. Configure local client adapters: SharkBay 只配置当前成员本机安装的 clients。优先使用 project/workspace-local 配置；如果某个 client 只能全局配置，则必须做 repo path gating，不能让其它项目看到本项目 harness。
  6. Enable team sync: 用户开启 Teamwork 时，SharkBay 用 gh 检查身份和 repo 权限，并创建或 fetch sharkbay-team-context 分支。

File Contract

Harness 文件不进正常代码分支。普通 docs/ 仍然是 repo source docs； harness runtime files 留在本地 ignored .sharkbay/；completed context 写入独立 context branch。Agent 可以读大部分本地 harness 文件，但关键状态必须通过 SharkBay MCP/tool 修改。

Path Git Writer Reader Role
docs/ code branch normal tasks human, agent, help generator source documentation and durable decisions
.sharkbay/harness/instructions/*.md ignored SharkBay agent clients through local adapters client-specific local bootstrap instructions pointing to SharkBay protocol
.sharkbay/harness/protocol.md ignored SharkBay agent clients through local adapters current run rules, task lifecycle, claim policy, commit boundary
.sharkbay/harness/tools.json ignored SharkBay agent and MCP adapter available tool manifest and write boundaries
.sharkbay/tasks/*.json ignored SharkBay SharkBay and tools one JSON source-of-truth per local task
.sharkbay/claims/file-claims.json ignored SharkBay SharkBay and tools cross-task file ownership and blockers inside this worktree
.sharkbay/cache/github-users.json ignored SharkBay Tasks UI cached GitHub login, id, and avatar URL for task owners
.sharkbay-team-context/ sharkbay-team-context sync command team SharkBay instances completed compact task packages and searchable team context

Local Instruction Template

.sharkbay/harness/instructions/*.md 是本地生成文件，不进 repo。 它们应该短、稳定，只放当前项目的 SharkBay harness 入口，不放当前 task 细节。 

# SharkBay Agent Guide

This repository uses the SharkBay harness for team task context.

Before doing project work:
1. Read `.sharkbay/harness/protocol.md` if it exists.
2. Use SharkBay MCP tools for task lifecycle, team context search, file claims, run events, and sync preparation.
3. If the user request is project work, create or continue a SharkBay task before editing.
4. Do not edit files until the harness grants a file claim for your task.
5. If a needed file is claimed by another task or dirty with no owner, stop and report the blocker.
6. Commit only files owned by your task.

Project rules:
- Keep source documentation in `docs/`.
- Keep runtime task state out of git; `.sharkbay/` must stay ignored.
- Do not write secrets, credentials, customer data, or raw private transcripts into shared context.
- Mark verification as `combined_worktree` unless SharkBay provides an isolated clean worktree.

Useful commands:
- Use project package scripts for build/test when available.
- Use `rg` for local search.
- Use `gh` for GitHub issue, PR, and permission checks when Teamwork is enabled.

Protocol File

.sharkbay/harness/protocol.md 是 SharkBay 本地生成的当前协议。 它比 client-specific instruction 更具体，包含当前 harness 状态和工具入口。 

# SharkBay Harness Protocol

Generated: 2026-05-15T10:35:00Z
Project: SharkUI/SharkBay
Worktree: /Users/shark/Projects/SharkBay-generic
Branch: teamwork
Implicit current task: none. Every task-specific tool call must include `taskId`.

## Required Flow
1. Load project context with `get_project_context`.
2. If the user request is project work, call `create_or_continue_task`.
3. Read the returned task with `get_task(taskId)`.
4. Search team context with `search_team_context` when prior work matters.
5. Before editing, call `claim_files` for every target file.
6. If claim fails, pause and record a blocker with `record_run_event`.
7. After edits, record verification scope and result.
8. Prepare a task package with `prepare_task_export`.

## File Claim Outcomes
- `granted`: edit is allowed for this task.
- `waiting_for_file`: file belongs to another active task.
- `dirty_unowned_file`: file is dirty but has no known task owner.
- `stale_claim`: SharkBay needs user recovery before editing.

## Commit Boundary
- Stage only files owned by the task.
- Do not include unrelated dirty files.
- Do not start sync until the task has a commit, blocked summary, or abandon decision.

Agent Client Adapter

当前 SharkBay 支持多个 agent CLI。Tasks UI 不展示某个 client 的 bootstrap 能力；只有用户点击具体 agent button 时，SharkBay 才应用该 client adapter。 Adapter 负责选择启动命令、可选 initial prompt、本地 instruction file 和本机 project-scoped MCP 配置方式。 

Agent client adapter fields:
- id: codex | claude | gemini | kiro | deepseek | qwen | opencode
- command: executable path
- instructionFiles: .sharkbay/harness/instructions/<client>.md
- initialPrompt: supported | unsupported | unknown
- mcpConfig: project-local | workspace-local | gated user config | unsupported
- statusLogs: how SharkBay reads progress, if known

Launch behavior:
1. User clicks a specific agent button.
2. SharkBay starts that CLI in repo root.
3. If the client supports an initial prompt, adapter may pass a short bootstrap prompt that only points to instruction files and MCP tools.
4. If not, user can manually tell the agent to read `.sharkbay/harness/instructions/<client>.md`.
5. SharkBay never writes harness instruction files into the repo.
6. The agent creates/continues tasks through SharkBay MCP tools.

Bootstrap prompt 不能包含当前 task、文件列表、Issue 摘要或裁剪后的项目上下文； 这些信息必须由 agent 读 instruction files 后通过 MCP 显式获取。

File Claim Guard

并行 task 的冲突边界是文件。agent 准备修改文件前，必须先通过 harness claim 文件；harness 检查 Git dirty state 和 file-claims.json 后决定是否允许。 这个规则必须在工具层执行，不能只靠 prompt 约束 agent。file-claims.json 只能由 SharkBay harness 写入；claim 更新必须是原子的，写入前读取当前 revision， 写入时用 compare-and-swap 或 lock file 防止两个 agent 同时 claim 同一个 clean file。 

Claim rules:
- clean + unclaimed file: allow, then add to requesting task ownedFiles
- already claimed by requesting task: allow
- claimed by another active task: pause requesting task as waiting_for_file
- dirty + no known owner: pause requesting task as dirty_unowned_file
- deleted/renamed file: require explicit claim for old path and new path
- generated files: claim only if they will be committed with this task

Task commit 时只 stage 自己的 ownedFiles。如果 verification 在同一个 worktree 中运行，结果必须标记为 combined worktree；需要更强保证时， SharkBay 应提示用户在 clean temporary worktree 或独立 worktree 中做 isolated verification。

Task Conflict Flow

当 task 要修改被其他 task claim 的文件时，暂停的是当前 task，不是整个 worktree。用户可以继续推进其它不相关 task；等占用文件的 task commit/sync 或释放 claim 后，再回到暂停 task 点击 continue。 

Task B wants src/browser/fullscreen.ts
-> file claimed by Task A
-> Task B status: waiting_for_file
-> user finishes Task A and commits ownedFiles
-> SharkBay sees file clean/unclaimed
-> user continues Task B
-> agent refreshes task/context through MCP and continues

File Claim State

file-claims.json 是 worktree-local 的轻量 lock table，不是团队级锁。 它只用于防止同一个 worktree 内多个本地 agent 互相覆盖 dirty files。

Active Task Recovery

SharkBay 启动或进入项目时必须检查 .sharkbay/tasks/*.json、 .sharkbay/claims/file-claims.json 和 .sharkbay/harness/events.jsonl。 如果某个 active task 超过默认 24 小时没有 event 更新，或上次 session 没有正常关闭， 就标记为 stale。

术语边界：export 是生成 compact task package；sync 是把 package 写入并推送到 sharkbay-team-context。UI 只向用户暴露 sync 状态，例如 pending sync 或 sync failed。

  • resume: 继续指定 task，保留它的 owned files 和 run logs。
  • finish/sync: 用户确认 summary、verification 和 commit 后生成 package 并同步到 context branch。
  • mark blocked: 生成 blocked task package 并 sync；释放或保留 file claims 由用户决定。
  • abandon: 只有该 task 的 owned files clean，或用户明确 stash/clean 后才允许。

Sync 或 abandon 失败必须保持 active task 文件不删除，UI 显示明确的 pending/recovery 状态。 不允许静默丢弃 .sharkbay/ 状态。

Help Site

Help site 是 post-MVP 的本地生成物，不进 repo。MVP 可以先在 Tasks tab 直接展示 active tasks、file claims、completed task summaries 和 search results。

  • 触发：MVP 后先支持用户手动生成；后续可在 fetch context branch、完成 sync、或打开 Tasks tab 时增量刷新。
  • 内容：默认包含 active tasks、file claim 状态、最近 50 个 completed tasks、最近 90 天 run summaries、相关 docs index、open GitHub issues/PRs 摘要。
  • 范围：完整历史不默认渲染，可通过 search 或 archive page 按需展开。
  • 位置：~/Library/Application Support/SharkBay/help-sites/<project-id>/。

不按成员建目录。成员身份放在每条 context record 的 metadata 中，而不是塞进长文件名。 这样文件仍然按类型和时间聚合，同时 UI 可以按成员、机器、agent、branch、时间和状态过滤。

Conflict Policy

Teamwork context 的冲突策略是 append-only、unique file 和 duplicate-on-conflict。 SharkBay 不做 destructive merge，不覆盖其他成员写入，也不把 Git conflict 暴露给用户。

  1. 写入前 fetch 最新 sharkbay-team-context。
  2. 在临时 worktree 中新增唯一文件并 commit。
  3. push 成功则完成。
  4. 如果 push rejected，fetch 最新后 rebase 并重试。
  5. 如果 rebase 真的发生文件冲突，abort rebase，基于最新远程重新生成唯一文件名，再 commit + push。
  6. 如果仍失败，将待同步文件保存到本机 pending queue，UI 显示 Team context pending sync。

语义冲突不在 Git 层解决。例如两个 agent runs 对同一个 issue 给出互相矛盾的建议， SharkBay 保留两条记录。真正的产品或架构结论应该通过 GitHub Issue/PR 讨论后进入 docs/，而不是在 runtime context 分支里合并成 decision。

Tasks UI

现有 SharkBay 是三栏工作台：左侧项目列表、中间 terminal/browser、右侧 detail panel。 Tasks 应作为 Project detail 的第一个 tab，放在 Git 左边，不新增独立 dashboard。

  • Tab and panel title: Tab title 永远是 Tasks。Harness 未安装或 Teamwork 未启用时 panel title 是 Harness；Teamwork sync 启用后 panel title 是 Teamwork。
  • Status subpanel: 一行 facts，显示 repo、branch、worktree、gh actor、repo permission、context sync、active task count、claimed files count。
  • Task list: Tasks 是一个一体化列表，不按 active/completed 拆 panel，也不再套一个写着 Tasks / All 的 subpanel 标题框。列表直接出现在 Teamwork status 下方。
  • Task tag: 不使用顺序编号。每个 task 生成一个 6 位 taskTag，例如 A7K3P9。完整 taskId 使用 A7K3P9-u3960864-m7f3a6。
  • Task order: task 按状态优先级和更新时间排序，不按 tag 排序。
  • Task row: Teamwork 启用时左侧显示 GitHub 头像，头像 URL 来自 gh api 并缓存到 .sharkbay/cache/github-users.json；未启用 Teamwork 时左侧不显示编号，列表直接以 title 开始。title 是主视觉，subtitle 显示 taskTag、owner、sync result、blocking file、commit/time 或 verification scope；task list 不显示 machine。sync failed、waiting_for_file、dirty_unowned_file 都是 task row 状态；waiting 使用黄色 warning 状态。
  • Task detail: 点击 task 后列表消失，右侧 panel 进入 task detail drilldown。Detail 顶部有 back button 返回 task list；标题下不重复 project/type/status。详情只展示任务事实，例如 status、branch/base、verification、sync result、blocked-by 文件和 related runs。正常 claimed files 默认不展示，只有 claim 冲突、dirty unowned 或阻塞其它 task 时才露出。
  • Task creation: Tasks tab 不负责创建 task，也不放 Quick task、Task、Create from issue 这类按钮。task 从 agent client 里的工作互动产生；Tasks tab 只展示、切换、恢复和查看详情。
  • Attention rows: 只显示非 task 归属的风险，例如 context branch risk、gh readiness 问题；task 自身问题留在对应 task row 和 task detail。

Issues 和 Help site 不进入 MVP 首屏：Issue 可以作为 agent client 对话里的上下文来源， 但不在 Tasks tab 里提供独立 task 创建按钮； Help site 是 post-MVP 本地生成物。

Boundaries
  • 基础 SharkBay 不要求 gh，扫描项目、开终端、本地 agent run 仍可用。
  • Teamwork 功能要求 gh authenticated。
  • 写入共享 context 要求 GitHub repo permission 至少是 write。
  • Policy 配置建议要求 maintain 或 admin。
  • .sharkbay/ 保存本地 active tasks、file claims 和 harness state，必须通过本地 .git/info/exclude 或 SharkBay commit guard 排除，不能要求修改 repo .gitignore。
  • 同一 worktree 可以有多个 active editing tasks；并发边界是文件 claim，不是 worktree clean。
  • agent 修改文件前必须 claim file；遇到被其他 task claim 或 dirty 但无 owner 的文件时，当前 task 暂停。
  • 同一用户可以在多个 worktree 有多个 active tasks，但 UI 必须显式展示 repo、branch、worktree 和 claimed files。
  • Runtime context 分支只保存完成后的 tasks/ 和关键 runs/ 摘要。
  • GitHub Issues 是 task 的可选来源；重要决策使用 docs/。
  • Raw transcript 可以后续再做，MVP 先记录可审计摘要和关键 events。
  • 严肃审计如果未来变强，再引入 SharkBay backend 或 GitHub App。

Architecture Risks

Risk Impact Mitigation
Context branch 被 force-push 或删除 团队历史丢失或不可追溯 创建 sharkbay-team-context 时提示配置 branch protection；SharkBay 检测 protected 状态并在未保护时显示风险。
gh token 过期或权限变化 用户以为 context 已同步，但实际失败 每次 sync 前运行 readiness check；失败时保留 pending sync，UI 明确显示未同步，不删除 active task。
同一 worktree 多个 active tasks 的验证被污染 Task A 的测试可能在 Task A + Task B 的组合状态下通过，不能证明单独提交 A 后通过 verification 记录必须标注 combined worktree 或 isolated clean state；高风险 task 提示使用独立 worktree 验证。
File claim stale 或 SharkBay 崩溃 文件被旧 task claim，导致新 task 无法继续 启动时检测 stale active tasks 和 file claims，提供 resume、release claim、finish/sync、mark blocked、abandon recovery options。
