# SharkBay 全面工程审计计划

编制日期：2026-11-17。状态：计划待执行；本文不代表审计已经完成。

本次审计的主要目标是系统发现 SharkBay 长期演进中积累、尚未充分暴露的潜在缺陷和工程债务，并通过后续修复提升性能、可靠性、安全、代码质量、测试有效性和文档质量。范围覆盖整个项目，包括业务正确性、架构与状态设计、资源管理、数据与权限边界、依赖以及构建发布流程。

审计从全项目的模块、业务流程与工程机制出发，建立质量基线，识别隐藏问题和共性根因，再形成可验证的改进路线。历史故障和近期改动作为检查样本与风险线索，不决定审计范围和完成标准。

审计先收集证据，再分批修复。现有功能、状态机或文档不能仅因复杂、旧、缺少静态引用而被判定为无用；同样，现有代码和测试也不能自动证明产品行为正确。

## 1 审计目标和完成标准

本轮需要回答以下问题：

1. 长期迭代在业务逻辑、模块交互、边界条件、异常处理与兼容路径中留下了哪些潜在缺陷？哪些问题尚未被现有测试或日常使用暴露？
2. 典型工作负载下的性能瓶颈、重复工作和资源浪费在哪里？规模增长后有哪些退化或失控路径？
3. 正常运行、并发操作、取消、断连、部分失败与恢复时，系统能否保持正确、可预测和可恢复？
4. 文件、Git、数据、网络、凭据和外部执行的安全边界是否完整？是否存在越权、注入、泄露或数据损坏路径？
5. 模块职责、依赖和状态归属是否清楚？是否存在重复实现、冗余状态、不必要的状态机、孤儿模块和过期兼容逻辑？
6. 代码复杂度、耦合、隐含约定和缺失契约是否增加理解、修改和回归风险？哪些简化可以持续降低维护成本？
7. 测试、文档和实现是否共同准确表达产品规则？现有验证机制能否发现问题并阻止再次引入？
8. 构建、安装、升级与日常维护机制能否持续交付一致、可信的产品？

### 1.1 质量基线与改进验证

每个领域同时检查已有缺陷、潜在风险和可验证的改进机会。先记录现状，再为具体改进设置验收指标；无法直接量化的结构问题使用调用关系、业务契约和变更影响作为证据。

| 维度 | 基线内容 | 后续改进的验证方式 |
| --- | --- | --- |
| 性能 | 典型流程耗时与延迟分布、吞吐、重复工作、CPU、内存、磁盘及随规模增长的变化 | 相同环境和输入下比较修复前后结果，确认收益且没有转移成本或损害正确性 |
| 可靠性与正确性 | 业务不变量、失败传播、超时与取消、恢复行为、并发一致性和资源生命周期 | 正常、边界、异常与恢复场景符合契约，失败可识别，数据和状态保持一致 |
| 安全 | 信任边界、入口校验、权限、敏感数据流和依赖暴露面 | 对应威胁与未授权输入被正确处理，修复关闭可达路径，合法操作继续可用 |
| 代码质量 | 职责与依赖、重复规则、状态归属、复杂热点、孤儿和兼容负担 | 用途与归属清楚，必要行为保留，已证实的重复与无用机制减少，修改影响更可控 |
| 测试质量 | 关键行为和风险的验证缺口、断言有效性、隔离与稳定性 | 能发现对应缺陷或契约破坏，执行可靠且没有生产副作用，不以测试数量替代效果 |
| 文档质量 | 规范与现状的差异、术语冲突、过时方案、重复和遗漏 | 产品规则、实现、测试与使用说明一致，历史资料身份清楚且入口可追踪 |

### 1.2 完成标准

审计完成需要满足：

- 13 个审计领域均有检查记录、证据和结论；没有执行的验证必须列明原因与影响。
- 所有业务入口、自有模块、主要副作用和状态存储都有覆盖记录与责任归属；跨模块流程及高风险路径完成从入口到副作用、再到清理的追踪。
- 性能、可靠性、安全、代码、测试和文档质量均有现状评估、改进机会与对应验收办法，不能用复现历史故障代替某个领域的系统检查。
- 资源、状态机、遗留代码、测试和文档差异形成可追踪清单。
- 每个确认问题都有严重程度、影响、触发条件、代码位置、修复建议和验证方式。
- 既记录具体缺陷，也识别跨模块的共性根因和预防措施；改进建议说明收益、代价与实施顺序。
- 最终报告区分审计覆盖完成、问题修复完成和发布验收完成，分别报告剩余风险。

## 2 当前约束和执行边界

### 2.1 本轮允许的工作

- 静态阅读源码、历史、文档、测试和构建配置；检查现有日志与构建产物时先脱敏。
- 审查测试和脚本的副作用，再按明确的文件清单执行模块级隔离测试。
- 使用临时配置、临时 Git 仓库、合成日志和假进程验证边界行为。
- 将确认问题、待验证假设和修复建议写入报告。

### 2.2 继续保留的限制

- 不启动已安装或新打包的 SharkBay，不附着、重启或停止用户正在使用的实例。
- 不启动完整 ApplicationRuntime 或应用服务入口；需要它们的集成测试先静态审查，运行验收留待后续授权。
- 不更新或部署到 103，不执行远程变更，不发布 Release 或自动更新包。
- 不在真实 Orca 或其他日常仓库上重建 CodeGraph，不做真实项目的高负载扫描。
- 不修改真实的 `~/.sharkbay`、Agent 会话目录、Git 凭据、系统设置或正式更新源。
- 不执行真实 GitHub 写操作、Telegram 发送、协议同步、依赖自动升级或批量自动清理。

当前请求的交付是审计计划。后续审计中的修复作为独立批次实施；删除功能、大规模迁移和正式发布不由本计划自动授权。若用户后续调整限制，记录新的授权范围，其他限制继续生效。

### 2.3 隔离要求

- 每个运行用例明确列出输入路径、写入路径、网络目标、子进程和清理方式。
- 配置、数据库、socket、终端、缓存和输出均使用本轮专属临时目录；不依赖默认目录回退。
- 检查继承的环境变量、Git 配置和凭据发现行为。测试通过依赖注入或受限执行环境隔离真实会话与用户数据。
- 如果模块无法注入会话目录或无法禁止真实网络访问，先记录隔离缺口，不能以“使用了临时 config”代替完整隔离。
- 临时配置隔离不等于资源隔离。大样本、真实索引和长时间负载测试安排在有系统级内存、CPU、磁盘与进程配额的独立环境；不在日常 Mac 上直接扩大负载。
- 监督进程在被测进程之外运行，记录进程树；超限只终止本轮创建并验证身份的进程，不按名称批量结束进程。

## 3 范围和审计基线

### 3.1 产品约束

以 [AGENTS.md](../AGENTS.md) 中的现行产品约束为审计依据：GitHub 是唯一身份、权限和协作系统；SharkBay 服务于 Issues、PR 和隔离 worktree 生命周期；本地状态是执行投影。现有实现、历史设计和测试中的相反假设都需要检查。

产品规则与实际行为分开记录：用户指令和明确的产品决策用于判断应有行为；源码、测试和运行证据用于确认实际行为。二者冲突时记录问题，不能简单以代码覆盖产品约束，也不能只改文档掩盖实现缺陷。

### 3.2 代码和资料范围

| 范围 | 内容 |
| --- | --- |
| 桌面与界面 | `electron/`、`src/renderer/`、`src/island/`、其他页面与 preload、样式及资源 |
| 服务与核心 | `src/server/`、`src/runtime/`、`src/core/`、`src/main/`、插件、执行提供方、调度和配置机制 |
| 共享契约 | `src/shared/`、IPC、应用命令与事件、schema、类型及序列化 |
| 测试与工具 | `tests/`、测试配置、`scripts/`、构建配置、依赖锁文件、实际存在的 CI 和发布流程 |
| 文档与设计 | 根目录说明和指令、`docs/`、脚本说明、仓库内开发指引、历史设计、代码注释与 TODO |
| 产物与外部边界 | 现有安装包、运行时依赖、原生模块、CodeGraph、Agent CLI、Git/gh、Telegram、更新源和 Homebrew 部署资料 |

自有源码逐模块覆盖；依赖、生成文件和构建产物进行来源、内容、版本与边界检查，不逐行审读第三方全部源码。未纳入的外部服务与平台组件明确列在范围限制中。

### 3.3 基线记录

计划编制时 HEAD 为 `45a492088a0a68cd3813b896a64ef914200e5355`，工作区存在大量已修改和未跟踪文件。全部相关内容均纳入当前实现基线，不按修改时间筛选审计范围。执行前重新记录：

- HEAD、分支、时间与时区、完整变更清单，以及纳入范围文件的内容指纹。
- 暂存、未暂存、未跟踪内容分别保存为受控快照；不提交敏感资料，不覆盖用户改动。
- Node、Electron、包管理器、操作系统和硬件环境；依赖声明、锁定版本、实际安装与随包版本分别记录。
- 需要比对的已发布版本和本地测试包，记录来源、版本、构建时间与文件校验值。

审计主对象是冻结的当前工作区快照。已发布版本另建对照基线，避免把当前修复当成已发布行为。执行期间出现新改动时明确增量范围，不混合两份基线给出结论。

### 3.4 长期演进与历史证据

- 先建立全项目模块、业务流程、数据与状态机制清单，再结合历史识别职责变化、重写与迁移、并存的新旧方案和失去退出条件的兼容逻辑。
- 历史回溯服务于当前问题的用途、契约和根因判断；按需要追踪关键变更，不以最近提交或曾经报错的文件替代全量覆盖。
- 长期未修改、没有现成测试、缺少文档或看似稳定的模块同样纳入检查；已有修复和已通过测试的实现也需要核实其假设与边界。
- 历史故障、已修复缺陷与用户反馈用于建立回归样本和寻找同类问题。本机与 103 的故障属于其中的案例；具体事故因果分析作为相关发现的补充证据，不作为本轮审计的主线或完成条件。

## 4 十三个审计领域

每个领域都要记录已查模块、入口、相关测试、已确认问题、待验证项和未覆盖边界。

### 4.1 资源与性能

- 检查启动、项目切换、文件监听、转录轮询、用量回填、终端快照、状态广播和日志写入的工作量。
- 为常用操作建立冷启动与热路径、空闲与繁忙、小规模与多项目的性能基线；检查关键延迟、渲染与传输开销、批处理、缓存命中和重复计算，寻找日常性能改善机会。
- 检查整文件读取、同步 I/O、超大 JSON 解析、无界 `Promise.all`、重入扫描、缓存、队列、重试和消息缓冲。
- CodeGraph 检查索引触发、候选文件筛选、并发、取消、超时、子进程树、数据库增长及失败后的重试；验证打开项目不会自动索引。
- 分别测量 JS 堆、RSS、原生内存、进程树、CPU、磁盘读写、句柄、监听器、队列和事件循环延迟，不能只用 JS 堆判断内存安全。
- 产出资源清单：每项资源的创建者、上限、取消点、释放点、超限行为和验证证据。

### 4.2 进程生命周期与异常恢复

- 从桌面启动、runtime 发现、握手、锁获取、初始化到停止逐段追踪；检查并发启动和部分初始化失败。
- 验证关闭客户端与停止 runtime 的不同语义；检查 PTY、Agent、监听器和后台任务的所有权。
- 检查失效锁、活进程锁、PID 复用、权限失败、损坏锁、恢复竞争以及中断的恢复保护目录。
- 检查超时是否终止真实子进程及后代，清理是否幂等，异常是否导致后续任务永久阻塞。
- 检查错误分类与传播、重试退避和上限、取消传播、依赖不可用和部分成功；明确各模块的失败契约，防止静默失败、重试放大和错误被错误层级吞掉。
- 通过假进程和临时锁验证；需要完整应用生命周期的部分列入后续集成验收。

### 4.3 状态与并发正确性

- 为 Agent、终端、任务、调度、索引、Telegram turn、更新器及界面状态逐项建立状态和事件清单。
- 检查事件来源、会话身份、版本、顺序、时钟、重复、过期、撤销、并发更新和异步结果回写。
- 对状态合并验证“内部状态及时准确、语义变化及时通知、重复更新有界、尾部更新不丢失”；覆盖持续事件流而非仅短 burst。
- 检查多个客户端重连、控制权移交、晚到响应、项目切换和对象销毁后的事件归属。
- 产出状态归属表、迁移表、业务不变量与冲突案例；详见第 6 节。

### 4.4 仓库与文件操作安全

- 检查 clone、worktree 创建与清理、分支切换、merge、协议安装和卸载、项目移除、文件编辑及缓存删除。
- 覆盖未提交、未跟踪、冲突、detached HEAD、linked worktree、子模块、损坏仓库和 Git 命令失败。
- 检查路径规范化、符号链接、相对路径、大小写、删除边界和校验后路径发生变化的情况。
- 检查命令参数中的空格、引号、换行、前导连字符和 shell 元字符；明确用户主动执行命令与输入被意外拼接执行的区别。
- 只在临时仓库中验证；比较操作前后的文件内容、Git 引用和工作区状态，错误路径也必须保留用户数据。

### 4.5 数据持久化与一致性

- 清点 JSON、SQLite、localStorage、索引、会话、缓存和迁移版本，明确哪些是事实、投影或可重建缓存。
- 检查单写入者、原子写入、事务、修订号、部分成功、迁移幂等性和备份恢复。
- 注入写入中断、损坏或截断文件、权限失败、磁盘写入失败与数据库 busy；不通过填满宿主磁盘模拟磁盘满。
- 检查 GitHub 权限变化、离线、限流、重试和远程删除后的校准，避免本地旧投影覆盖远程事实。
- 验证恢复后数据没有静默丢失或误报成功，缓存重建不会自动触发不可控工作。

### 4.6 权限与外部输入

- 按 Electron 页面、远程网页、preload、IPC、控制 socket、HTTP/WS、插件和外部工具划分信任边界。
- 检查上下文隔离、Node 访问、导航和新窗口、权限请求、CSP、HTML/Markdown 渲染与外部链接处理。
- 检查 IPC sender、命令 schema、项目授权、socket 权限、网络绑定、认证、Origin、跨站请求、会话失效和消息大小限制。
- 验证桌面、浏览器和 Telegram 等入口是否执行相同的必要校验；插件或执行提供方能否绕过边界。
- 使用畸形输入、未授权身份、跨项目路径和伪造事件做拒绝测试；所有网络行为限定在测试环境。

### 4.7 凭据与隐私

- 追踪 GitHub、Telegram、共享链接、配对和控制会话凭据的生成、存储、传递、失效与删除。
- 检查日志、异常、进程参数、终端快照、导出内容、Agent transcript 和发布包中的敏感信息。
- 清点网络出口和发送内容，核对是否符合功能和用户授权；检查撤销权限或取消配对后的行为。
- 只使用假凭据验证脱敏与访问控制，不将真实凭据或原始会话复制到审计报告。
- 发现真实泄露时停止扩散该材料，记录脱敏证据并给出处置建议。

### 4.8 依赖与供应链

- 对比依赖声明、锁文件、实际安装和随包版本，检查重复、无用、过期、维护状态、来源及许可证与 NOTICE。
- 分开检查 Electron、Chromium、Electron 内置 Node、独立 Node、原生模块和外部 CLI。
- 核实漏洞公告对应的版本、运行入口、可达性和现有缓解，不能把扫描器条目直接等同于可利用缺陷。
- 检查下载校验、安装脚本、动态插件加载、命令搜索路径和原生 ABI；新增扫描工具先审查其安装与运行副作用。
- 提交依赖处置建议，不运行自动升级或 `audit fix`，不为取得扫描结果上传私有源码。

### 4.9 构建发布与升级

- 检查构建输入、干净输出、文件排除、产物清单和源码指纹；确认不会打入旧构建、测试、秘密或不需要的依赖。
- 检查架构、独立 Node、SQLite/PTY ABI、ASAR 布局和运行时路径；区分开发环境可用与安装包可用。
- 区分 ad-hoc 本地测试包与正式 Developer ID 签名、公证、staple；完整性校验、系统信任和启动成功分别记录。
- 检查更新源、签名与校验、失败重试、取消、版本兼容、客户端与存续 runtime 的协议兼容，以及数据迁移后的恢复策略。
- 静态审查 Homebrew 和 103 的部署路径；真实安装、更新和部署验收留待后续授权，不接触正式源。

### 4.10 产品边界与可诊断性

- 核对功能、身份、权限、任务与协作状态是否符合 GitHub 原生协调工具的定位。
- 核对 Projects、Workspace、Task、Session、Profile、Provider 等概念是否有稳定含义，界面与文档是否使用同一术语。
- 检查等待、后台执行、取消、失败、过期和部分成功能否被用户区分；确认按钮反馈与真实副作用一致。
- 检查启动阶段、命令、子进程和异常是否能通过请求、任务、终端与会话标识关联，避免日志因频繁写入反过来放大负载。
- 静态审查界面和纯逻辑；需要实际桌面渲染与交互的验证列入后续验收。

### 4.11 测试体系与测试代码质量

- 逐个测试文件分类：纯函数、临时文件、子进程、本地服务、完整 runtime、桌面、真实外部集成；检查导入时副作用、setup 与 teardown。
- 建立风险到测试的映射，检查异常、边界、取消、重复、并发、乱序、迁移和历史事故回归；覆盖率作为定位线索，不作为正确性的替代指标。
- 检查空断言、错误对象断言、未等待的 Promise、吞掉异常、过度 mock、mock 与真实接口偏离，以及只验证实现细节的测试。
- 检查被跳过、长期失效、重复或仅支撑旧实现的测试；区分无意义重复与有价值的跨边界回归。
- 检查随机性、时钟、固定端口、执行顺序、共享状态、监听器、进程和定时器泄漏；对疑似不稳定用例有针对性地重复验证。
- `npm run lint` 当前仅执行 typecheck；审计实际检查能力，不把脚本名称当成已经完成语法、风格或安全检查的证据。

### 4.12 代码结构与历史遗留

- 为每个自有模块标明用途、生产入口、调用者、外部消费者、数据和副作用；检查重复实现、职责漂移和跨层依赖。
- 清点孤儿模块、无用导出、不可达分支、旧 IPC/事件、失效配置、废弃插件与依赖；检查只被测试调用的实现是否仍有产品入口。
- 检查前端、runtime、Electron、浏览器和不同 Agent connector 对同一规则的复制与分叉。
- 检查循环依赖、越层访问、隐式初始化顺序、接口职责、复杂分支和隐含契约；追踪局部修改为何会扩散为多模块变更及回归风险。
- 清点旧迁移、兼容层、临时 fallback、功能开关、TODO 与重复重试机制，核对保留理由和退出条件。
- 状态机、缓存或抽象层只有在明确用途、代价和替代方案后才能建议移除；不以文件大小、年龄或枚举数量认定缺陷。
- 每个候选清理项按第 7 节取证，形成可独立审阅的小批清理方案。

### 4.13 文档质量与实现一致性

- 清点文档、指令、设计稿、注释与示例；逐份标明当前规范、当前实现说明、未实施提案或历史资料。
- 对产品定位、术语、流程、状态定义、命令、目录、配置、默认值、接口、权限、构建和发布步骤建立事实对照。
- 核对根指令、Product、Architecture、Testing、Release、Workspace 与各设计方案之间的冲突，避免旧方案继续指导新实现。
- 检查重复段落、孤儿文档、断链、遗漏的新功能、过时示例及注释与行为相反的情况。
- 命令先静态检查，不为验证文档而直接执行启动、安装、发布或清理命令。
- 产出“文档声明—实现证据—产品约束—处理决定”差异表，明确应修文档、修实现、修测试还是补充产品决策。

## 7 孤儿代码和清理项的判定方法

每个候选项需经过以下核对：

1. **发现**：使用文本引用、TypeScript 导入和符号关系、构建入口、注册表及必要的历史回溯提出候选。
2. **反证**：排查动态 import、字符串 IPC、插件 manifest、命令行入口、资源文件名、包导出、外部 hook、兼容客户端与迁移链。
3. **用途判断**：确认是否仅为测试而存在、是否被新实现取代、是否还有数据或版本兼容职责；缺少静态引用只能标为候选。
4. **影响分析**：列出删除或合并涉及的消费者、持久化格式、测试、文档、依赖和回退条件。
5. **处置验证**：在后续修复批次做最小删除或合并，验证原有业务行为，移除由该变更造成的孤儿内容。

纯清理与行为修复分批提交，避免混合后无法归因。优先删除已经证明无用途的内容；保留必要兼容逻辑时记录依据。只有重复实现已产生维护代价且存在更简单的共同规则时，才提取共享抽象。

### 8.1 资源测量规则

- 首轮使用最小能复现的样本，一次只运行一个被测工作负载，禁止默认并行跑满测试机。
- 每项测试启动前固定内存、CPU、磁盘增量、子进程数和时长预算；未填写预算或没有外部监督时，不运行资源压力用例。
- 记录空闲基线、峰值、结束后值和随时间的变化；一次普通样本通过不能证明任意仓库规模安全。
- 对流式读取，扩大总输入量时，保留内存应受块、单条记录、队列和消费者缓冲上限约束；对索引等需要随数据增长的工作，记录增长模型与拒绝或取消边界。
- 超时、系统内存压力恶化、进程或队列持续增长时停止测试；保留证据，不在日常机器上反复扩大规模。
- 堆上限不能替代 RSS、原生内存、子进程和磁盘配额。堆快照本身有额外开销，仅在隔离预算允许时采集。
- 除生命周期趋势测试外，首次仅做足以区分回归与噪声的少量重复；只有波动或疑似泄漏才扩大次数。量化验收阈值在测试前固定，不根据结果事后放宽。

### 8.2 现有命令的执行规则

| 命令或入口 | 当前计划中的处理 |
| --- | --- |
| `git diff --check`、受控文件清单和引用搜索 | 静态验证使用，避免输出敏感原文 |
| `npm run typecheck` | 审查脚本后用于对应基线的类型检查 |
| `node scripts/check-source-graph.mjs` | 审查后验证 runtime 导入边界；不能替代全项目用途分析 |
| `./node_modules/.bin/vitest run <已审查的文件列表>` | 只执行允许清单；检查所用 Vitest 版本支持的并发限制并纳入预算 |
| `npm test` | 不作为第一步直接执行；完整集合包含 runtime 集成测试，当前范围内保持筛选 |
| `npm run verify:webui`、`npm run verify:shared` | 会启动服务或桌面等进程，先静态审查，运行延后 |

## 9 问题分级和证据格式

### 9.1 严重程度

| 等级 | 判定依据 | 处置 |
| --- | --- | --- |
| P0 | 已确认存在现实触发路径的严重数据损失、广泛权限突破或整机失去响应等紧急风险 | 停止相关动态验证，优先提出遏制与修复方案 |
| P1 | 高影响的资源失控、越权、关键流程错误或恢复失败 | 优先修复，相关路径验收前不扩大使用范围 |
| P2 | 影响有限且有规避方式的错误，或已产生实际维护风险的不一致、重复状态和文档缺陷 | 按依赖关系分批修复 |
| P3 | 无直接行为影响的明确冗余、轻微文档问题和可维护性改进 | 与高风险修复分开安排 |

严重程度同时考虑触发条件、影响范围、可恢复性和利用难度。未确认的高影响假设记录潜在等级和证据缺口，不因猜测直接宣布为 P0。

### 9.2 每个发现的必要字段

- 编号、标题、领域、严重程度、证据可信度和当前处理状态。
- 基线、文件位置、受影响版本、入口及调用或数据流。
- 触发条件、预期行为、实际行为、影响范围和已有缓解。
- 最小复现或静态证明、命令与退出码、脱敏证据位置。
- 根因；尚未证实时写成待验证假设，并注明需要什么证据。
- 最小修复建议、兼容与迁移影响、验证方式和后续责任。
- 对应的质量目标、改进收益、实施成本与关联共性问题；尚未表现为缺陷的改进机会单列，不虚构故障或安全等级。

证据可信度分为已复现、静态确认、待验证；处理状态分为待处理、修复中、已验证、接受风险或已排除。修复完成必须有对应验证，不能只因代码已改就关闭。

| 交付物 | 内容 |
| --- | --- |
| `report.md` | 项目质量现状、基线、13 项覆盖、重要发现与共性根因、改进目标、限制及剩余风险 |
| `findings.md` | 按第 9 节记录的问题台账，包括已排除项的理由 |
| `inventories.md` | 模块与入口、资源所有权、状态迁移、清理候选、测试分类和文档差异六类清单 |
| `verification.md` | 环境、测试输入、执行记录、预期与实际、性能与可靠性基线、质量改进对比、失败归因和清理结果 |
| `remediation.md` | 按风险与收益组织的修复及质量提升路线、依赖与批次、兼容与迁移、每批验收和后续授权 |

大日志、原始会话、数据库和安装包保留在访问受限的本地证据目录；仓库只记录脱敏摘要与校验值，不将敏感原件提交到 Git。

### 10.2 修复顺序

1. **严重风险修复**：优先处理已确认的数据损失、安全突破、关键行为错误和资源失控路径。
2. **共性根因与质量提升**：按影响、收益、依赖和成本组织可靠性、性能、安全及状态设计的改进，不把近期事故相关模块固定为优先对象。
3. **结构与遗留治理**：处理已证实的重复规则、冗余状态、孤儿入口、过期兼容、无用依赖及高耦合热点；按独立影响范围拆分，必要行为保持兼容。
4. **文档与测试同步**：贯穿每批修复，统一产品术语、归档历史设计、补足有效验证与预防机制，避免改进后再次漂移。
5. **综合与发布验收**：取得后续授权后验证整体质量目标，以及安装、升级、完整生命周期与部署行为。

每批保持问题、变更与证据一一对应。只运行与改动相称的检查；发生新失败或出现未解决风险时再扩大验证，不为了追求指标增加重复测试或大规模重构。

## 11 最终验收清单

- [ ] 审计基线包含未提交和未跟踪的相关改动，执行结果可以对应到确切内容。
- [ ] 13 个领域都有检查范围、证据、结论和明确的未覆盖项。
- [ ] 长期未修改、缺少测试或文档的模块与跨模块流程均纳入覆盖，审计没有局限于近期改动和已知故障。
- [ ] 性能、可靠性、安全、代码、测试和文档质量均有现状评估、改善机会与可验证目标。
- [ ] 具体缺陷与跨模块共性根因分别记录；历史案例用于回归与同类问题检查，因果判断有证据。
- [ ] 核心资源有所有者、上限、取消与释放路径，异常路径经过可执行范围内的验证。
- [ ] 核心状态机制有迁移与归属表，重复状态和清理候选均有用途及兼容证据。
- [ ] 测试文件、脚本副作用、断言质量和隔离缺口已审查，完整应用测试没有被误执行。
- [ ] 文档的规范、现状、提案与历史角色清晰，关键冲突都有处理决定。
- [ ] 高风险发现有最小修复方案，清理建议可独立审阅，没有夹带无关重构。
- [ ] 实际执行的测试没有修改真实配置和仓库，没有遗留本轮进程或后台任务。

## 12 方法参考

以下资料用于补充检查方法，不替代 SharkBay 的具体产品约束与证据：

- [Electron Security](https://www.electronjs.org/docs/latest/tutorial/security)：用于检查桌面内容、preload、IPC、权限和依赖边界。
- [Node.js Don't Block the Event Loop](https://nodejs.org/en/learn/asynchronous-work/dont-block-the-event-loop)：用于检查同步工作、大输入处理和事件循环阻塞。
- [NIST Software Verification](https://www.nist.gov/itl/executive-order-14028-improving-nations-cybersecurity/software-supply-chain-security-guidance-2)：用于组织威胁分析、静态检查、依赖检查、异常输入与行为测试的组合。
