# 语义界面设计

## 核心命题

不要把 UI 设计成一组装下功能的页面。把它设计成产品模型对用户的清晰投影：用尽可能少、稳定且可迁移的概念，让用户无需解释就能理解系统、预测行为并完成任务。

优先减少“需要学会的概念”，而不是单纯减少元素数量。视觉上的简洁如果仍要求用户理解多个模式、入口、窗口或例外规则，就不是真正的简洁。

## 先建立立场

在画界面或修改代码前，先形成一份简短、明确的语义模型：

- 用户此刻真正要完成的任务是什么？
- 用户认为自己在操作哪些对象，而不是代码里有哪些模块？
- 对象之间有哪些关系？哪些只是对象的状态、视图或能力？
- 哪些结构和行为必须跨状态保持不变？
- 产品已经教会用户哪些全局交互语法？
- 当前方案新增了什么用户必须记住的概念？

把结论压成一句有取舍的设计主张。不要以多个看似都可行的通用选项代替判断。

当方案存在真正的架构分叉时，分别构造支持和反对它的最强论证，定位会改变结论的关键变量。只有当这个变量无法从产品和代码中确认、且不同答案会改变产品模型时，才向用户问一个决定性问题；否则继续执行。

## 遵守语义约束

### 保持对象身份稳定

同一个对象在空、加载、完成、错误、编辑等状态下仍应是同一个对象。尽量维持同一入口、同一容器、同一空间锚点和同一套基础操作，只让与状态相关的内容和能力发生变化。

不要因为实现模块不同，就让用户进入不同的产品世界。先判断差异属于对象、状态、视图还是能力：

- 只有对象身份、核心任务、权限边界或生命周期真正不同，才考虑新建顶层界面。
- 状态变化优先在稳定结构内表达，不为每个状态复制一套界面。
- 能力优先组合进对象的工作空间，不把每项能力升级成新的模式或流程。
- 视图可以切换，但必须保持对象身份、未完成工作和方向感。

### 复用全局交互语法

一致性不是外观相似，而是相同语义拥有相同的入口、反馈和结果。先调查产品中已经存在的选择、引用、编辑、提交、撤销、切换和快捷键行为，再扩展它们。

局部方案只有在可以成为全局规则时才值得引入。不要为单个页面发明特例，也不要让鼠标、键盘或不同入口对同一动作产生不同语义。

### 让结构承担解释

通过位置、分组、顺序、控件形态、状态反馈和内容本身说明界面。把解释性副标题视为设计失败的信号：先修正信息架构和控件，而不是补一行“这里可以做什么”。

只保留会改变用户判断的文字，例如对象名称、状态、结果、限制和必要的领域信息。不要用标题重复容器已经表达的含义，不要用占位文案掩盖空洞结构，也不要让 tooltip 承担主流程说明。

控件必须符合其语义：

- Tab 只承载同一层级、相互并列的视图或能力；切换 Tab 不应等同于执行动作或跨越对象。
- Button 表示动作，selection 表示选择，navigation 表示去往另一位置；不要只因视觉方便而混用。
- 优先采用成熟、可预期的控件形态。新颖性必须换来真实能力，而不是换皮。

### 按相关性分配界面

只显示当前状态、当前对象和当前任务真正需要的信息与操作。相关性为零的区域应消失，而不是留下标题、空容器或说明文字证明它存在。

渐进披露应跟随意图和状态，而不是隐藏核心能力。高频主路径直接可见；精确参数、低频设置和高级能力在需要时出现。不要让所有可能性同时争夺注意力。

### 用层级表达决策价值

视觉权重必须与用户此刻的决策价值一致。先确定主对象、主要动作、辅助信息和系统状态，再分配空间、对比、颜色与字号。

使用少量、按角色定义的字号和字重，保持同类信息一致。不要逐元素微调出一套大大小小的临时字号。优先得到平静、清楚、有方向感的界面，而不是装饰丰富的界面。

## 执行工作流

### 1. 观察完整系统

检查真实产品、相关流程、现有组件和实现约束。寻找全局语法及其例外，区分用户问题与局部视觉症状。不要只根据一张截图或用户点名的控件直接打补丁。

### 2. 写出状态与能力矩阵

对重要界面列出：

| 项目 | 必须回答的问题 |
| --- | --- |
| 对象 | 用户认为自己正在操作什么？ |
| 状态 | 哪些变化不应改变对象身份？ |
| 稳定结构 | 哪些区域、位置和行为应跨状态保留？ |
| 状态内容 | 每个状态真正需要显示什么？ |
| 能力 | 哪些操作是并列能力，哪些是流程动作？ |
| 隐藏条件 | 什么在不相关时必须彻底消失？ |
| 全局语法 | 入口、引用、选择、编辑和提交如何复用产品既有规则？ |

如果矩阵暴露出重复界面、同义入口或状态间结构跳变，先修正模型，再继续视觉设计。

### 3. 先定信息架构，再定样式

依次决定对象身份、区域职责、导航层级、操作层级和状态反馈。然后才决定布局尺度、控件外观、颜色、字号和动效。

对每个新增区域或控件进行概念预算审查：它是否表达了用户必须理解的新概念？如果只是现有对象的状态或能力，能否并入既有结构？

### 4. 实现完整行为

实现主路径及其必要状态，而不是只拼静态外观。保持焦点、键盘与鼠标语义一致，保护未提交输入，提供清楚且就近的反馈，并满足基本的可访问性、目标尺寸、对比度和响应式要求。

修改现有产品时，优先消除导致问题的结构性原因。不要用新的包装层、模式开关或解释文案覆盖旧模型的矛盾。

### 5. 在真实渲染中验证

构建成功和测试通过只能证明实现没有明显破坏，不能证明界面设计成立。必须打开真实界面并检查：

- 主任务是否无需说明即可开始和完成；
- 空、加载、错误、完成和切换状态是否保持对象与空间连续性；
- 当前无关的区域是否真正消失；
- Tab、按钮、选择、引用和快捷键是否符合全局语法；
- 文字层级是否来自一套稳定尺度，是否仍有解释性副标题；
- 常见视口下是否出现拥挤、漂移、截断、弱对比或错误焦点。

发现问题后回到语义模型判断原因，修正并重新验证。不要把截图润色当作产品验证。

## 输出标准

给出具体、可执行且有立场的结论。先说明采用的用户模型和关键取舍，再说明界面结果；不要罗列任何项目都能套用的“最佳实践”。

每次交付前确认：

- 用户需要理解的概念是否更少，而不是仅仅元素更少？
- 用户能否根据已有经验预测下一步和结果？
- 同一对象、动作和关系是否始终使用同一语法？
- 控件和结构能否自我说明，且没有解释性副标题补救？
- 新功能是否作为能力被组合，而不是制造新模式？
- 信息和视觉权重是否与当前任务相关？
- 是否已经检查真实渲染与状态转换？

任一答案为否，都不要宣称设计完成。
